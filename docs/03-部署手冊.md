# 部署手冊（GitHub → Railway）

## ⚠ Railway 改咗規矩，同你八字專案唔一樣

Railway 已把 **Config as Code（`railway.json` / `railway.toml`）標記為淘汰**：

- 既有服務可繼續使用到 **2026-12-01 硬性截止**
- **新服務已經不能再選用**

所以呢個專案一開始就用 **Infrastructure as Code**：`.railway/railway.ts`，
配 `railway` npm SDK，由 CLI 執行 plan / apply。

順帶一提：**你的八字專案若仍在用 `railway.json`，記得在截止日前遷移。**
做法是 `railway config pull` 讓 CLI 讀取現有專案設定並產生 `railway.ts`，再逐步接管。
同一個服務不能同時由兩套系統管理，`railway config plan` 會直接擋下並指出哪個服務要先遷移。

另外，新服務的預設建置器已由 Nixpacks 換成 **Railpack**；不過只要 repo 裡有 Dockerfile，
Railway 一定用 Dockerfile。本專案前後端都自帶 Dockerfile，所以建置行為是確定的。

## ⚠⚠ 最重要的一步：Root Directory

這是個 monorepo。**每個 service 都必須指定 root directory**，否則 Railway 由 repo
根目錄看起，見到的是兩個並列的子目錄，判不出要建什麼。

| Service | Root Directory | 建置方式 |
|---|---|---|
| `api` | `/backend` | 有 Dockerfile → 用 Dockerfile |
| `web` | `/frontend` | 有 Dockerfile → 用 Dockerfile |

Railway 一見到 Dockerfile 就必用 Dockerfile，不會再跑 Railpack。所以只要
root directory 設對，建置行為就是確定的。

**repo 根目錄刻意不放 `package.json`。** 根目錄一有 `package.json`，Railpack 就會
把整個 monorepo 誤判成 Node app，然後抱怨找不到 start script。Railway IaC 需要的
`railway` SDK 改放 `.railway/package.json` —— 該檔只由 CLI 讀取，不影響 runtime。

## 步驟

### 1. 推上 GitHub

```bash
cd ziwei-lab
git init && git add -A && git commit -m "紫微斗數排盤系統：核心引擎與部署骨架"
git remote add origin git@github.com:你的帳號/ziwei-lab.git
git push -u origin main
```

### 2. 安裝 CLI 與 SDK

```bash
curl -fsSL https://railway.com/install.sh | sh   # 需 CLI 5.2.0 以上
(cd .railway && npm install)                      # IaC 用的 railway SDK
railway login
railway link                                      # 選專案與環境
```

### 2b. 兩條路，揀一條

**路線 A —— 接 GitHub（建議）**：在 Railway 建兩個 service，各自
Settings → Source 接上同一個 repo，再設 Root Directory 為 `/backend` 與 `/frontend`。
之後 push 即自動部署。用 CLI 設：

```bash
railway environment edit --service-config api source.rootDirectory /backend
railway environment edit --service-config web source.rootDirectory /frontend
```

**路線 B —— `railway up` 直接上傳**：CLI 上傳的是「當前目錄」的快照，
所以必須在子目錄內執行，令快照根目錄就是含 Dockerfile 那層。已封裝成 `deploy.sh`：

```bash
./deploy.sh api    # 等同 cd backend && railway up --service api
./deploy.sh web
./deploy.sh all
```

在 repo 根目錄直接 `railway up` 是行不通的 —— 那正是前面兩次建置失敗的原因。

### 3. 改 `.railway/railway.ts`

把 `REPO` 改成你的 repo，把 `ziwei.example.com` 改成你的網域（或先刪掉 `domains`）。

### 4. Plan → Apply

```bash
railway config plan     # 先看 diff，秘密值預設遮蔽
railway config apply    # 確認後才動手
```

`plan` 支援 `--detailed-exit-code`：無變更回傳 0、有待套用變更回傳 2。
CI 已用這招在 PR 階段偵測設定漂移。

### 5. 設定秘密

`JWT_SECRET` 在 IaC 檔中標記為 `preserve()`，代表「保留 Railway 現有值」，
不入版本庫。在 Railway 介面或 CLI 設定：

```bash
railway variable set JWT_SECRET="$(openssl rand -hex 32)" --service api
```

### 6. 驗證

```bash
curl https://<api-domain>/health
# {"status":"ok","service":"紫微斗數分析系統"}
```

## 本機開發

```bash
# 後端
cd backend && pip install -r requirements-dev.txt
uvicorn app.main:app --reload          # :8000，/docs 有 OpenAPI

# 前端
cd frontend && npm install && npm run dev   # :5173，已設 /api 代理
```

## 幾個部署上的坑

**sxtwl 是 C++ 擴充。** 後端 Dockerfile 裝了 `build-essential`，因為 sxtwl 2.0.7 不保證
每個 Python 版本都有預編譯 wheel。若建置時間太長，可考慮改用 `sxtwl-modern` 分支，
它提供較新的 Python 版本 wheel；但要先跑一次完整迴歸測試確認結果一致。

**前端不要另加 nginx。** `server.mjs` 用單一 Node 程序靜態伺服 `dist/`，
並把找不到的路徑回退到 `index.html`。少一層鏡像、少一份設定。

**`PORT` 由 Railway 注入**，兩個 Dockerfile 都已讀取，不要寫死埠號。

**健康檢查**指向 `/health`。若 `strict_tables=true` 而流派表未填完，
`/chart` 會拋錯但 `/health` 仍正常 —— 這是刻意的，好讓你分得清是服務掛了還是資料未備妥。
